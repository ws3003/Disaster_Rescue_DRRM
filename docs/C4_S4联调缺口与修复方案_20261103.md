## 2. 已修复：边缘接收时间被丢弃

复现：源 readings.edge_received_at 非空，Worker 同步确认成功后，S4-06 返回同一 reading_id 的 edge_received_at=null。

根因：`src/sync/worker.py::_read_business` 的 reading 分支漏带该字段。服务端 `_write_business_copy` 已接收它，S4 0.1.0 的读数 DTO 也已定义它。

修复：发送该现有元数据字段；不修改 canonical 白名单、内容哈希规则、S4 接口、数据库 schema 或时间字符串语义。

- 改动前检查 Git 状态并备份：`_backup/B_before_c4_edge_received_fix_20261103_b2a69d4df30641f085c954d2d0fc3038`。

## 3. 未解决：人员告警确认同步，但服务端没有事件副本

实际软件测试：

1. 在独立边缘库用 bridge 创建 `high_risk_alert` 类型的 person_event，确认 Outbox queued。
2. Worker 经实际 C4 路由发送，源 Outbox 状态 success。
3. 独立服务端库没有对应 events 业务记录；S4 人员列表返回空。

根因：两端 `_BUSINESS_CARRIERS` 仅包含 reading/sensor_alert。person_event 只发送 record_type/source_record_id/content_hash；接收端只登记 c4_idem，不写 events。

影响：即使同步状态显示 success，小程序也查不到这条人员告警；不能拿同一个 SQLite 同时当边缘库和服务端库来掩盖缺口。

待确认的修复方向（尚未实施）：

- 保持 S4 0.1.0 不变，在 C4 人员事件的已有 records/business 结构中明确业务副本语义，携带既有事件 ID、原始 ts、type、severity、person_id 和 payload；字段选择和校验需明确确认。
- 服务端同一事务完成 hash 核验、c4_idem 登记和 events 副本写入；保留原始 naive ts，不用接收时间代替、不追加时区。
- 同键同内容不新增事件；同键异内容保留冲突审计、不覆盖原始副本。
- 兼容历史“仅登记但缺业务副本”的已确认记录：升级后同键同 hash 且缺副本时应能补齐，否则升级代码仍会永久漏数据。补齐策略也需纳入确认及测试。
- 还须从真实 Agent 告警产生处验证入 Outbox 的接线。本轮用例显式调用 bridge，不能证明原有 Agent 自动产生的人员告警已经入队。
- 对 PC 接收端、Pi 发送端和生产接线安排配套升级；保留旧客户端行为及历史数据，不静默把 metadata-only 回执当成完整业务交付证据。

## 4. 未解决：传感器告警恢复后服务端仍为 active

实际软件测试：

1. 传感器告警第一次同步，服务端状态 active。
2. 边缘使用现有 update_sensor_alert_status 将同一 alert_id 改为 resolved，resolved_at 有值。
3. 再运行 Worker，没有待发送的状态更新；S4 详情仍为 active。

根因：当前恢复操作仅更新边缘行；已完成的 Outbox 记录不重新调度。Worker 的 sensor_alert 本体也未携带 status/resolved_at，接收端同 hash 重放只确认，不推进生命周期。

影响：小程序显示的活动状态可长期落后于 Pi 实际状态；重复运行当前 Worker 无法解决。

待确认的修复方向（尚未实施）：

- 保持稳定 alert_id、现有 S4 字段及告警条数，明确 C4 对已定义 status/resolved_at 的生命周期传播语义。
- 以 active→resolved 单调推进为边界；旧 active 重试不能把已恢复副本改回 active。解决重放顺序问题，而非简单“覆盖最后一次收到的状态”。
- 恢复写入与重新安排同步必须原子化，避免“边缘已恢复但待同步任务丢失”；沿用现有租约/gen fencing，旧发送者不能用过期回执覆盖新调度状态。
- 同 hash 的允许状态推进与严格防重规则需明确确认；不要为解决更新而随意改 canonical 白名单、添加未确认接口或伪造新的业务字段。
- 验证服务端异常、回执丢失、旧 active 延迟重试、重复 resolved、重启恢复、唯一副本及 resolved_at 保留。
