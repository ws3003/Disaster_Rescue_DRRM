## §3 三项已确认决策

### §3.1 Agent 契约测试（4 项）→ `KNOWN_BASELINE_DEVIATION`
用户决定：**暂不修复，保留 V4.3 冻结边界**。不改 `src/agent/` 冻结逻辑、不删测试、不降断言、不伪报通过，与 V4.4 新增功能测试分开统计。
**诊断结论（已推翻"memory.py 导致"初判）**：`bridge.create_sync_record(person_event)` 连续两次均成功写 2 条 `memory_alert`；真实 Agent 流程中 `record_alert` 仅被调用 1 次；`src/agent/agent.py:479-489` 已提交逻辑通信成功后立即 `break` → 多人员只录第一条。**结论**：4 项失败为已提交 Agent 执行行为与契约测试预期不一致（既有偏差），不能归因于未提交 memory.py 的数据库写路径。

### §3.2 `src/agent/memory.py` → 恢复 V4.3 行为（审核通过后单独 P0，本轮不执行）
- **恢复目标（精确）**：未提交改动把 `record_alert` 内 `self.db.save_event(type="memory_alert", severity=..., person_id=..., payload={...})`（HEAD L577-595）替换为 `c4_bridge.create_sync_record(record_type="person_event", business={...})`（工作区 L578-596）。恢复=将块改回 `save_event` 形式。
- **约束**：只改 `src/agent/memory.py`；不改 `src/agent/` 其他文件；不新增旁路同步 Worker；不扩大 C4 范围；保留其他未提交修改。恢复前看完整 diff 与 HEAD 版本，恢复后核对该文件差异已消除且其他文件无影响。
- **旁注（不处理，记录备查）**：原改动使 person_event 落入 `c4_verify`（reason=`unparsable`）而非 Outbox，未达成 C4 同步；恢复即取消该路径。

### §3.3 微信登录 → 不在 B 线交付范围
保留 `server/auth.py`、`server/wechat.py`、`tests/test_auth.py`、`users/sessions` 表，不删、不续开、不纳入 B 线验收；仅分析与 S4 契约关系。
**与 S4 契约关系（分析）**：`s4_contract.json` 规定 `authentication.no_login_issue_refresh_revoke_endpoints=true`、scope 仅五个 S4 GET；设计基线 §12.2 批准 S4 入站为单一 Bearer Token、不新增 `/login`。`auth.py` 实现的是微信用户会话登录（/login /me /logout），与 S4 入站语义**不一致但互不依赖**（S4 每端点走 `_require_s4_token` 服务令牌）。二者可并存，但契约文档须在"微信登录"与"S4 Bearer"间明确界限。本轮**不将 `/login` 纳入 B 线交付**。

### §7.3 数据库增量迁移策略（可执行方案）
`CREATE TABLE IF NOT EXISTS` 只能保证新表幂等，**不等于完整迁移**。采用如下技术方案（本轮只写入计划，不实现迁移代码）：

1. **新表创建**：在 `schema.sql` 追加 `CREATE TABLE IF NOT EXISTS ...`（幂等，重复执行安全），由 `db.py` 初始化应用。
2. **已有表加字段**：`IF NOT EXISTS` **不迁移列**。采用守卫式迁移：先 `PRAGMA table_info(<table>)` 检查字段是否已存在，缺失时才执行 `ALTER TABLE ... ADD COLUMN ...`。
3. **不使用** `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，**不假设**当前 SQLite 版本支持该语法；统一走第 2 条的字段守卫。
4. **迁移版本管理**：引入位点表 `schema_migrations(version INTEGER PRIMARY KEY, applied_at TEXT)`（或等价 `PRAGMA user_version`）。
5. **按序执行**：启动时读取已应用位点，只执行尚未应用的迁移，按版本升序。
6. **位点—DDL 一致性**：迁移 N 的 DDL 与写入位点 N 在同一连接完成；**仅当迁移成功后才写入位点**，失败不落位点。
7. **`executescript()` 不作为原子回滚事务**：其前置隐式 COMMIT、无法保证整段原子回滚，**不把**含迁移 DDL 的 `executescript()` 当作事务方案；对新加列等需原子执行的迁移，采用显式事务控制，并核实现有 `with_transaction()` 的真实行为后再确定接入方式。
8. **失败处理**：迁移失败抛出错误；数据库初始化失败**不得启动业务**。
9. **迁移前备份**既有数据库文件。
10. **迁移后核对 V4.3 原有表**：`persons`、`events`、`tasks`、`agent_logs` 结构存在且数据完好（`PRAGMA table_info` + 行数抽查）。
11. **保留旧数据**：禁止 `DROP`、重命名或改变既有字段语义。
12. **新增字段**优先使用兼容旧数据的默认值（如可 NULL 字段）。
13. **归口**：数据库文件唯一负责人为 **B**（§8）；C 组申报需求，D 组经 B 交接后使用；共享文件修改一律由负责人实施。

## §10 每阶段测试和验收标准

- **每模块完成后**：运行其单元测试全绿（新增 + 既有相关）。
- **回归基线**：`python -m pytest tests/`；4 项 `test_contract_authoritative` 计入 `KNOWN_BASELINE_DEVIATION`，与 V4.4 新功能测试分开统计；`test_api_gateway` 遗留登记待评估；**X4 14 项（服务端 13 项 + HTTP 传输 1 项）**与 V4.3 语音 5 项按 §2 归类处置。
- **不**以"改冻结逻辑/删断言/跳过测试"换通过。
- **验收分层（L1→L8）**：L1 单元/契约 → **L2 真实传感器（拆三档，见下）** → L3 真实摄像头取证 → L4 真实 OSS → L5 C4 真机同步/断网 → L6 S4 真实库 → L7 云边协同时真模型 → L8 端到端主流程。
- **L2 三档分开登记（温度通过≠湿度通过≠完整温湿度链通过）**：
  - **`L2-Temperature`**：DS18B20 设备已确认（`28-0224e33f1e4e`/GPIO4），需真实接线与 Pi 运行环境验证；可独立记录验证结果。
  - **`L2-Humidity`**：湿度传感器型号**尚未物理确认**（不凭 I2C 地址猜型号）；当前 `BLOCKED`。
  - **`L2-Full`**：必须同时完成真实温度与湿度采集、完整温湿度链路验证；温度通道通过不代表完整链路通过。
- E7-01 只能以"温度通道验证通过（`L2-Temperature`）"的限定形式登记，直至湿度（`L2-Humidity`）落地、完整链（`L2-Full`）通过。

## §12 Pi-Windows 联合测试计划（与 §6 云端优先一致）
